# 진행/완료 문서 테이블 분리 효과 측정

## 목적
진행 문서(hot)와 완료 문서(cold)를 물리 테이블로 분리한 설계가 실제 조회 성능에 얼마나 영향을 주는지,
분리 전 구조(통합 테이블)와 같은 조건에서 비교한다.

## 측정 환경
| 항목 | 값 |
|---|---|
| DB | MySQL 8.4.11 (로컬), InnoDB, REPEATABLE READ |
| 버퍼 풀 | 128MB (기본값) |
| 데이터 | 사용자 1,000명 / 완료 문서 1,000,000건 / 진행 문서 10,000건 / 결재선 문서당 3~5줄 |
| 측정 사용자 | `perf_user_0001` (결재대기 16건, 기안한 진행 문서 10건, 전체 결재선 이력 4,040줄) |
| 측정 방법 | 같은 쿼리를 한 번 실행해 버퍼 풀을 데운 뒤 `EXPLAIN ANALYZE` 의 actual time 기록 |

- 데이터 생성: [`sql/01_generate_data.sql`](sql/01_generate_data.sql)
- 측정 쿼리: [`sql/02_hot_cold_compare.sql`](sql/02_hot_cold_compare.sql)
- 원본 결과: [`results/02_hot_cold_compare.log`](results/02_hot_cold_compare.log)

### 공정한 비교를 위한 조건
- **같은 데이터**: 통합 테이블(`tbl_doc_all`, `tbl_aprline_all`)에 전체 데이터를 먼저 만들고, 거기서 진행/완료 테이블로 나눠 복사했다.
- **같은 인덱스**: 통합 테이블을 `CREATE TABLE ... LIKE tbl_activedoc / tbl_aprline` 으로 만들어 PK, `mem_id`, `activedoc_id` 인덱스가 동일하다.
- **같은 쿼리**: 앱(JPQL)이 생성하는 SQL 형태 그대로, 테이블 이름만 바꿨다.

### 비교 범위: 문서 마스터(`tbl_document_master`)는 왜 비교하지 않았나
- 분리는 **본문(`ActiveDoc` / `EndDoc`)과 결재선(`AprLine` / `EndAprLine`)에만** 적용되어 있다.
  `DocumentMaster` 는 문서의 출생신고서 역할이라 최종결재 후에도 삭제되지 않으므로, 현재 구조에서도 진행 + 완료 101만 건을 모두 가진다.
  통합 구조용 문서 마스터를 따로 만들어도 현재 테이블과 같은 복사본이 되므로 별도로 만들지 않았다.
- 측정한 결재대기함 / 기안함 쿼리는 `ActiveDoc`, `AprLine`, `UserMaster` 만 조인하고 `DocumentMaster` 는 읽지 않는다.
- 따라서 `DocumentMaster` 를 조건으로 사용하는 조회(예: 기안자 기준 검색)가 생기면, 그 조회는 분리의 혜택을 받지 못한다.

## 결과

### 테이블 크기
| 구조 | 문서 | 결재선 | 데이터 + 인덱스 |
|---|---:|---:|---:|
| 분리 (진행 테이블) | 1만 | 4만 | **약 9MB** |
| 통합 | 101만 | 404만 | **약 762MB** |

진행 테이블 전체가 버퍼 풀(128MB)에 여유 있게 올라가는 반면, 통합 테이블은 버퍼 풀의 약 6배다.

### 조회 성능
| 조회 | 결재선 인덱스로 읽은 행 | 문서 조인 횟수 | 분리 | 통합 | 차이 |
|---|---:|---:|---:|---:|---:|
| 결재대기함 목록 | 40 vs 4,040 | 16 vs 16 | **1.87ms** | 19.6ms | 약 10배 |
| 결재대기함 건수 | 40 vs 4,040 | 16 vs 16 | **0.56ms** | 20.1ms | 약 36배 |
| 기안함 목록 | 40 vs 4,040 | **10 vs 1,010** | **0.43ms** | 22.4ms | 약 52배 |
| 기안함 건수 | 40 vs 4,040 | **10 vs 1,010** | **0.38ms** | 21.7ms | 약 57배 |

## 분석
- 두 구조의 실행 계획은 **완전히 같다** (`login_id` 로 사용자 조회 → `mem_id` 인덱스로 결재선 조회 → PK 로 문서 조인).
  차이는 계획이 아니라 **인덱스가 가리키는 행의 수**에서 나온다.
- 통합 구조에서는 사용자의 결재선 인덱스(`mem_id`)에 **과거 완료 문서의 결재선까지 모두** 들어 있어,
  진행 중인 몇 건을 찾기 위해 4,040줄을 읽고 상태 조건으로 걸러낸다(결재대기함은 4,040 → 16).
- 기안함은 차이가 더 크다. 기안자 조건(`step_seq = 1`)으로 걸러도 과거에 기안한 문서 1,010건이 남고,
  각각을 문서 테이블과 조인한 뒤에야 진행 상태(`doc_status = '02'`)로 걸러져 10건이 된다.
- 분리 구조에서는 진행 테이블에 진행 문서만 있으므로 처음부터 40줄만 읽는다.
  사용자의 결재 이력이 쌓일수록(근속 연수, 문서량) 통합 구조의 비용은 계속 늘지만 분리 구조의 비용은 진행 문서 수에만 비례한다.

## 한계와 해석 시 주의점
- 절대 시간은 통합 구조도 약 20ms 수준이다. 단건 응답으로는 체감하기 어렵고,
  차이는 **요청이 몰릴 때의 누적 비용**과 **버퍼 풀 경쟁**에서 커진다.
  (참고: 버퍼 풀을 데우기 전 첫 실행에서 통합 구조 기안함 조회는 198ms, 분리 구조는 9.5ms 였다. 1회 관측값이라 정식 수치로 쓰지 않는다.)
- 통합 구조에서도 `(mem_id, approve_status)` 같은 복합 인덱스를 두면 결재대기함의 차이는 크게 줄어든다.
  분리의 장점은 "인덱스를 조회마다 맞춤 설계하지 않아도 작업 대상 데이터 자체가 1% 로 줄어든다"는 데 있고,
  대가는 최종결재 시 진행 → 완료 이관 비용과 두 구조를 오가는 조회 로직의 복잡도다.
