# 📑 전자결재 시스템 고도화 프로젝트

본 프로젝트는 실제 그룹웨어 유지보수(SM) 경험을 바탕으로, 기존 시스템의 비효율적인 구조를 개선하고 비즈니스 로직을 재설계한 **백엔드 중심 고도화 프로젝트**입니다.

---

## 1. 프로젝트 개요
* **목적**: 실무 결재 프로세스(기안-결재-완료) 구현 및 대용량 데이터를 고려한 DB 설계 
* **핵심 기능**:
    * 전자결재 기안 및 승인/반려 프로세스
    * 문서 상태(진행/완료)에 따른 물리적 테이블 분리 조회
    * TBL_STATUS_MAP(상태관리) 테이블을 별도로 구성하여 락경합을 줄이고 조회 성능향상을 도모
    * MyBatis 기반의 1:N 결재선 객체 매핑
    * 사용자 권한에 따른 동적 버튼 활성화 로직

---

## 2. 기술 스택 (Tech Stack)
* **Framework**: Spring Boot 3.x
* **Language**: Java 17
* **Database**: MySQL 8.0
* **ORM**: JPA, MyBatis
* **Build Tool**: Maven
* **Documentation**: Swagger (SpringDoc OpenAPI 2.3.0)
* **Security**: Spring Security

---

## 3. 핵심 설계 및 기술적 고민 (Technical Point)

### 3.1 효율적인 데이터 관리 (Table Partitioning Strategy)
* **고민**: 문서 데이터 누적 시 전체 조회 성능 저하 문제.
* **해결**: 진행 문서(`TBL_ACTIVEDOC`)와 완료 문서(`TBL_ENDDOC`)를 분리하여 설계. `STATUS_MAP` 테이블을 브릿지로 활용해 데이터의 생명주기를 관리하고 락경합을 줄이기 위해 상태관리에 필요한 가벼운 데이터 위주로 컬럼을 구성했습니다.

### 3.2 전략 패턴을 통한 결재로직 구현
* **고민**: 이전에 유지보수 당시 결재로직이 Switch case문으로 구성되어있어 결재코드자체가 매우 방대하고 유지보수가 어려워짐
* **해결**: 결재행위를 추상화하여 ApprovalAction이라는 인터페이스를 두고, 각 구현체에 결재로직을 작성토록 하여 유지보수 및 확장성을 향상시켰습니다.

### 3.3 비관적 락 활용
* **고민**: 문서에 대한 결재행위가 중첩될 경우 문서상태를 나타내는 데이터가 꼬여서 정합성이 깨지는 일 발생
* **해결**: 문서번호를 채번할 때와 문서상태값을 변경할 때 비관적 락을 걸도록 하여 데이터 꼬임을 방지

## 4. 아키텍처 v2.0 개편 (2026.09)

초기 설계(v1.0) 기반으로 구현 및 검증을 진행하던 중, **기존 DB스키마의 문제점**를 확인하여 데이터 모델링과 비즈니스 로직을 전면 리팩토링했습니다.

### 4.1 대리키(Surrogate Key) 도입 및 비식별 관계 전환
* **문제점:** 자연키 사용 시 PK값 변경 시 대응이 어렵고, 복합 자연키 식별 관계 사용 시 외래키 조합이 복잡해져 JPA 엔티티 매핑 및 유지보수 비용이 급증함.
* **개선:** 모든 테이블에 단일 인조 식별자(Auto Increment PK)를 적용해 비식별 관계로 전환하고, 기존 자연키는 비즈니스 검증용 `UNIQUE` 인덱스로 관리하여 엔티티 간 결합도를 대폭 낮춤.

### 4.2 데이터 정합성 문제 해결: 문서 상태관리 테이블 삭제
* **문제점:** `TBL_STATUS_MAP`과 `TBL_APRLINE`(결재선) 양쪽에 결재 상태가 존재하여, 결재선 단계 진행 시 두 테이블의 상태 동기화 실패로 인한 데이터 불일치 위험 확인.
* **개선:** 
  * 테이블을 제거함으로써 상태 중복 저장 원천 차단.
  * 현재 문서의 진행 상태는 문서 본체(`TBL_ACTIVEDOC`, `TBL_ENDDOC`)의 단일 컬럼으로 일원화.
  

### 4.3 연관관계 최적화
* 기존 `문서마스터 - 결재선` 간의 모호한 참조 구조를 실제 문서 엔티티(`진행/완료문서`)와 결재선 간의 직접적인 PK-FK 관계로 재설계하여 불필요한 조인 비용 제거.

### 4.4 확장성을 고려한 공통코드 도입
* 결재 유형, 문서 상태 코드의 유연한 확장을 위해 공통코드 테이블을 구축하고, 애플리케이션의 타입 안정성(`Enum`)과 변경 대응력(`DB 데이터 및 로컬 캐싱`)을 연계할 수 있는 구조 마련.

### 4.5 문서 복구를 고려한 문서이력 테이블 도입
* 전체 행 스냅샷용 테이블로 진행문서테이블 복구를 위한 문서이력 테이블 도입 




## 5. API 명세 (Swagger)
SpringDoc을 도입하여 별도의 문서 작성 없이 API 스펙을 관리하고 테스트 환경을 구축했습니다.

* **UI 접속**: `http://localhost:8080/swagger-ui/index.html`
* **주요 API**:
  - `POST /approval/draft`: 기안
  - `GET /approval/docDetail`: 문서 상세 및 결재선 조회
  - `POST /approval/process`: 승인/반려 처리
